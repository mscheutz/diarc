The human may provide various different types of input, whether it is giving the system an instruction, asking it a question, or providing it with information. No matter the type of input, the desired semantic form that the system can understand is called a predicate. A predicate takes the following form: <name>(<arguments>). <name> is simply a string, while <arguments> can be any number (0 to N) of symbols or nested predicates. Symbols are strings which may or may not have an associated type. Symbol types are denoted by a string following a colon. For example, an untyped symbol could be "testSymbol", while a typed symbol could be "testSymbol:testType".

The types known to the system are: physobj, location

Each specific type of user input (instruction, question, information) has a different set of valid predicate forms that can be mapped to. They will be described below:

Action Semantics:
Action semantics are used when the user is giving the system a direct instruction of an action it wants it to perform. The type of input in this case is INSTRUCT. Action semantics take the form: <actionName>(?actor,<arguments>).
<actionName> is the name of the action which the system knows how to perform and the user instructed in their command.
?actor is the agent in the system that the user instructed to perform the command. Again, the valid agents known to the system are self:agent. The actor of an action should default to self:agent if no specific indication of an actor is provided in the command.
<arguments> is a comma delimited list of the arguments to the instructed action.
Different actions can take in different numbers of arguments, anywhere between 0 and an arbitrarily large amount. Each argument is a symbol, which, as mentioned above, means that it may have an associated type. The type defines the set of values assignable to that argument. For example, an argument denoted as ?item:type1 in a semantic signature has the variable name ?item and type type1. The variable name is a placeholder to be replaced with the supplied value from the instruction, the type type1 denotes that the chosen value must be defined as a type1. If the user seems to supply a value for an argument which is not present in the current set of known entities of that type, there is no valid predicate to represent the input. In contrast, an argument denoted simply as, for example, ?varName has no type and does not have a restricted set of possible inputs. The exception to this rule is that ?actor must be an agent known to the system, though there may be different types of agents. Examples of types of arguments are the name of an area where the action is being performed, the objects which the action is being performed on, the duration which the action is to be performed over, and other types of information parameterizing the corresponding action.

Query semantics:
Query semantics are used when the user is asking the system a question in order to obtain information. The type of input in this case is QUESTION. Query semantics take the form <questionName>(<arguments>).
<questionName> is an arbitrary string representing the type of question being asked.
<arguments> is a comma delimited list of symbols or predicates parameterizing the question.

Below is the list of query semantics the system is able to parse, along with a description of what is being asked in each case:

Knowledge Semantics:
Knowledge semantics are used when the user is supplying the system with information or answering a question from the system. The type of input in this case is REPLY. Knowledge semantics can be any valid predicate, but typically take the form <typeOfInformation>(<valueOfInformation>).
